# Распознавание номерных знаков: YOLO11n и DeepSeek OCR

Сервис принимает кадр с камеры телефона, находит номерной знак, читает
символы и устойчиво подтверждает номер по нескольким кадрам. Для активности
«Выезд на место».

Два компонента, и только они:

**Детектор** — YOLO11n, обученная на нашем датасете, экспортированная в ONNX,
считается в этом же процессе **на процессоре**. Отвечает на вопрос «где на
кадре номер».

**Распознаватель** — `deepseek-ocr-2`, модель в кластере банка, доступная через
AI Gateway по сети. Отвечает на вопрос «какие символы на вырезе».

Никаких других моделей здесь нет. Это сделано нарочно: сравнения с другими
детекторами и распознавателями живут в отдельном исследовательском
репозитории, а здесь только то, что работает.

## Чем это является и чем не является

Это прототип. Распознавание работает и измерено, но справочник машин здесь
**тестовый**: файл с придуманными записями, нужный, чтобы сценарий
показывался до конца. Настоящего OCRM сервис не касается, и ответ на `GET /`
говорит об этом прямым текстом.

## Главное разделение, на котором держится сценарий

    номер прочитан          это распознавание
    машина найдена в базе   это поиск

Это два разных этапа. Номер, которого нет в базе, это **успешное
распознавание**, и сотруднику надо показать именно это: «номер распознан,
машина в базе не найдена». Иначе он будет переснимать исправно прочитанный
номер.

В коде это держится двумя способами: в ответе на кадр нет ни одного поля о
машине, и поиск отвечает кодом 200 с `found: false`, а не 404. На второе есть
отдельный тест.

## Запросы

| Запрос | Что делает |
|---|---|
| `GET /` | Кто это, какая версия, и что справочник тестовый |
| `GET /health/live` | Процесс жив. 200 и пока модель грузится |
| `GET /health/ready` | 503, пока модель не загружена, с причиной в ответе |
| `POST /api/v1/recognize` | Кадр, в ответ подтверждённый номер |
| `GET /api/v1/vehicle/{plate}` | Машина по номеру в тестовом справочнике |
| `POST /api/v1/visit` | Создать выезд в тестовом справочнике |
| `GET /docs` | Swagger с описанием каждого поля |

Пробы смотрят в разные места нарочно. Модель грузится несколько секунд, и если
`live` будет ждать готовности, кластер убьёт под на середине загрузки и начнёт
заново, и так по кругу.

### Кадр

```bash
# как есть в теле запроса: так шлёт страница съёмки
curl -X POST --data-binary @frame.jpg -H 'Content-Type: image/jpeg' \
     'localhost:8080/api/v1/recognize?session_id=phone-1'

# обычной загрузкой файла: удобнее для curl и Swagger
curl -F image=@frame.jpg 'localhost:8080/api/v1/recognize?session_id=phone-1'
```

```jsonc
{
  "ok": true,
  "plate": "545BDR05",          // подтверждённый номер, пусто если не подтверждён
  "confirmed": true,
  "changed": false,             // на этом кадре подтвердился ДРУГОЙ номер
  "bbox": [464, 359, 823, 448, 0.901],
  "confidence": 0.901,          // уверенность детектора: «здесь номер»
  "ocr_confidence": null,       // ВСЕГДА null, см. ниже
  "plate_type": "normal",
  "raw_text": "545BDR05",       // до нормализации, для разбора ошибок
  "session_id": "phone-1",
  "processing_time_ms": 198.4,
  "frame_size": [1280, 720],
  "ocr_variant_mode": "gateway",
  "profile": null               // разбивка по этапам, при profile=1
}
```

`ocr_confidence` всегда `null`, и это не недоделка. Распознаватель через шлюз
уверенности не возвращает, а поставить на её место число значило бы её
выдумать. Ноль читался бы как «прочитал, но совсем не уверен», тогда как на
самом деле это «уверенность неизвестна».

`session_id` это требование корректности, а не удобство. Подтверждение копит
прочитанное по времени, и при общем состоянии номер одной машины попадёт в
подсчёт другой. Один телефон это одна сессия.

`changed` это сигнал клиенту сбросить показанную карточку и запросить машину
заново.

## Как работает распознавание

```
кадр -> детектор -> рамка -> вырез -> шлюз -> нормализация ->
подсчёт совпадений -> подтверждённый номер
```

**Детектор** отдаёт одну рамку, самую уверенную. Сотрудник наводит камеру на
конкретную машину, ближайший номер он же и самый уверенный, а вторая рамка
породила бы вопрос, к какой машине относится ответ.

**Распознаватель** вызывается не на каждом кадре, а только после устойчивой
рамки, и это главное решение по производительности. Один вызов шлюза стоит
около 150 мс, то есть примерно весь бюджет кадра при трёх кадрах в секунду.
Экономить надо на числе обращений.

**Нормализация.** Формат номера известен: три цифры, три латинские буквы, две
цифры. По позиции символа видно, что там должно быть, а значит и какие
подмены распознавателя надо исправить: `O` вместо нуля, `I` вместо единицы и
так далее.

**Подтверждение по совпадениям.** Сервис не верит одному чтению. Номер
подтверждается, когда одно и то же прочитано нужное число раз в пределах
временного окна.

## Почему подтверждение именно по совпадениям

Это следствие того, что у распознавателя нет уверенности, и об этом стоит
прочитать целиком, потому что здесь легко сделать незаметную ошибку.

Обычное устройство такого слоя: взвешивать чтения уверенностью. Слабое чтение
отбрасывается, уверенное весит больше, одно очень уверенное подтверждает номер
сразу. Всё это требует, чтобы распознаватель возвращал уверенность. Ответ
`chat/completions` её не содержит.

Соблазнительное решение — подставить вместо неё единицу — ломает всё молча:
каждое чтение станет «очень уверенным», номер подтвердится с первого раза, и
слой устойчивости исчезнет. Сервис при этом будет выглядеть работающим, а
одна ошибка чтения сразу станет ответом.

Поэтому правило другое:

| | взвешивание по уверенности | по совпадениям (здесь) |
|---|---|---|
| Вес чтения | уверенность | одинаковый у всех |
| Слабое чтение | отбрасывается | не отбрасывается, отбрасывать нечем |
| Одно чтение подтверждает | да, при уверенности 0.95 | такого пути нет |
| Совпадений для смены машины | 2 | 3 |
| Окно | 1.5 с | 4 с |

Числа второго столбца **посчитаны, а не измерены**, и это надо проверить
замером. Три совпадения строже двух, потому что проверять уверенность каждого
чтения нечем. Окно шире, потому что один вызов шлюза это около 150 мс, чтения
идут только по кадрам с найденной рамкой, и совпадения набираются за секунды.

Цена подтверждения считается просто: три чтения по 150 мс это почти полсекунды
только на шлюз, плюс детектор на каждый кадр.

На это правило есть одиннадцать тестов в `tests/test_agreement_policy.py`, и
главный из них проверяет, что одного чтения недостаточно.

## Квадратные номера: честное ограничение

Квадратный двухстрочный номер читается **одним вызовом, целиком**, а не двумя
строками по отдельности.

Причина не в удобстве. Модель отдаёт номер одним текстом, разделить его на
строки нечем, а подсчёт по строкам требует, чтобы верхняя и нижняя приходили
отдельно. Плюс два вызова на кадр по 150 мс неподъёмны.

Следствие: на квадратных номерах устойчивость ниже, чем на однострочных. Кадр
с читаемой верхней строкой и смазанной нижней здесь не приносит пользы, тогда
как при построчном чтении приносил бы.

## Что известно про качество распознавателя

Замеры на лабораторной машине, сто вырезов части `test` из `datasets_ocr_kz`,
стенд `bench/ocr_engine_compare.py` из исследовательского репозитория:

| вариант входа | правильно | чужой номер | мс |
|---|---|---|---|
| вырез как есть | 44/100 | 3 | 150 |
| формулировка «plate» | 6/100 | 1 | 149 |
| вырез увеличен до 1024 | 46/100 | 5 | 353 |

Что из этого следует для работы.

**Формулировку запроса подбирать бессмысленно.** Это не модель, выполняющая
инструкции, а модель, которая транскрибирует изображение, и `Free OCR.` её
родной режим. Задача, сформулированная словами, сделала результат в семь раз
хуже.

**Увеличивать вырез не стоит.** Плюс два правильных чтения из ста и в два с
половиной раза медленнее. Поэтому `LPR_GATEWAY_UPSCALE` по умолчанию 0.

**Чужой номер верного формата это главная опасность.** Таких от одного до пяти
на сотню. Сервис покажет залог другой машины, и сотрудник не увидит подмены.
Подтверждение по совпадениям существует именно против этого.

### Чего мы с этой моделью сделать не можем

Обучить её. У нас есть только адрес шлюза, весов нет. В нашей власти только
то, что мы посылаем, как часто, и как обрабатываем ответ.

## Что известно про качество детектора

Отложенная выборка, 79 фотографий: 66 с номером, 13 без. Ни одной из них
модель при обучении не видела.

| порог | попала в номер | рамка мимо номера | не нашла | сработала на пустой |
|---|---|---|---|---|
| 0.25 | 64 из 66 | 0 | 2 | 0 |
| **0.40** | **64 из 66** | **0** | **2** | **0** |
| 0.55 | 62 из 66 | 0 | 4 | 0 |
| 0.70 | 58 из 66 | 0 | 8 | 0 |

Решающая колонка здесь вторая и первая. Сервис берёт **одну** рамку, самую
уверенную, значит ложная рамка вредит только тогда, когда обогнала настоящую.

Порог 0.40 выбран как верхняя граница, на которой ещё ничего не теряется.

**Порог свой у каждых обученных весов.** Переобучили модель — измеряйте
заново, см. `training/README.md`. Порог виден в ответе пробы готовности, в
поле `detector.min_conf`, чтобы по ответу сервиса было понятно, в каких
условиях получены его числа.

На процессоре детектор считает рамку за 20 мс. Это в семь раз дешевле одного
обращения к распознавателю, поэтому оптимизировать детектор смысла мало.

## Настройки

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `MODEL_PATH` | `/app/model/best11n_512.onnx` | Детектор. Файл или каталог с `.onnx` |
| `LPR_DETECT_CONF` | `0.40` | Порог уверенности детектора. Свой у каждых весов |
| `LPR_GATEWAY_URL` | пусто | Адрес шлюза до `/v1`. Без него сервис не станет готов |
| `LPR_GATEWAY_MODEL` | `deepseek-ocr-2/deepseek-ocr-2` | |
| `LPR_GATEWAY_TIMEOUT` | `10` | Секунд на один вызов шлюза |
| `LPR_GATEWAY_UPSCALE` | `0` | Увеличить вырез по ширине. Замерено: не стоит |
| `LPR_GATEWAY_PROMPT` | `Free OCR.` | Замерено: менять не стоит |
| `LPR_GATEWAY_KEY` | пусто | Ключ шлюза. **Только из Vault** |
| `ORT_THREADS` | `1` | Потоки математических библиотек |
| `MAX_FRAME_BYTES` | `10485760` | Предел на кадр, 10 МБ |
| `SESSION_TTL_SEC` | `1800` | Сессия без кадров столько секунд удаляется |
| `MAX_SESSIONS` | `1000` | Предел против роста памяти |
| `PLATE_HOLD_SEC` | `2.0` | Номер, который не читали столько секунд, снимается |
| `TEST_OCRM_FILE` | `config/test_ocrm.json` | Тестовый справочник |
| `SERVE_DEMO_PAGE` | `false` | Страница съёмки с телефона |
| `LPR_API_KEYS` | пусто | Ключи доступа через запятую. **Только из Vault** |
| `LOG_LEVEL` | `INFO` | |
| `ENVIRONMENT` | `dev` | |

Ни одного ключа в коде и в файлах репозитория нет и быть не должно. Пустое
значение `LPR_API_KEYS` означает, что проверка выключена, и сервис пишет об
этом в журнал при запуске, чтобы открытый режим не уехал в кластер
незамеченным.

`ORT_THREADS=1` не экономия: ONNX Runtime и OpenCV считают потоки по ядрам
**узла**, а не по квоте контейнера, и при квоте в одно ядро получаются десятки
потоков на одно ядро, где время уходит на переключение.

## Обучение модели

В папке `training/`, со своим окружением и своей инструкцией. Коротко: веса в
репозитории не хранятся, экспорт строго в 512, перед обучением проверка на
утечку, после обучения измерение порога и сквозная проверка по видео.

Ultralytics под лицензией AGPL-3.0 и стоит отдельно от сервиса. Сервис грузит
готовый `.onnx` через ONNX Runtime и об Ultralytics ничего не знает: граница
проходит ровно по папке `training/`.

## Деплой

Собран на шаблоне `python-fastapi-template`: FastAPI, UV, один include CI
`standard-service@v4.8.2`, деплой через AIDA.

Имена в `deployment/` это заготовки шаблона. Заполнять их руками не нужно:

```bash
aida init
```

выводит команду, владельца и имя сервиса из пути репозитория в GitLab.

| Событие | Что происходит |
|---|---|
| MR открыт | Проверки, тесты, `aida validate`, сборка без push |
| Влито в `test` | Тесты, сборка и push, **автоматический** деплой в TEST |
| Влито в `main` | Тесты, сборка и push, деплой в PROD **вручную** |

В образе лежит только модель детектора, 12 МБ. Весов распознавателя в образе
нет и быть не может: он работает по сети. Без локального распознавателя в
образе нет примерно гигабайта зависимостей.

Ресурсы в `deployment/values/default/values.yaml` поставлены с запасом и
**должны быть уточнены замером на живом сервисе**: процесс держит только
детектор, и прежние числа, снятые с локальным распознавателем, здесь не
годятся.

## Чего не хватает до продуктива

1. **Настоящий OCRM.** Справочник тестовый, записи придуманные. Меняется один
   файл, `app/api/ocrm.py`.
2. **Ключи доступа.** Путь в Vault не заполнен, сейчас кадры примет любой
   клиент.
3. **Привязка сессии к реплике.** Подсчёт совпадений живёт в памяти процесса,
   значит кадры одной сессии должны попадать на одну реплику. При двух
   репликах без sticky-сессий подсчёт начнётся заново.
4. **Ограничение частоты запросов.** Не сделано. Камера шлёт кадры
   непрерывно, и один клиент может занять всё ядро пода и всю квоту на шлюз.
5. **Измеренные числа правила подтверждения.** Сейчас они посчитаны.
6. **Поведение при недоступном шлюзе.** Сейчас кадр вернёт 503. Что должен
   видеть сотрудник, когда шлюз не отвечает, не решено.

## Где всё остальное

Сравнения детекторов и распознавателей, стенды, видео, разметка и все
измерения живут в исследовательском репозитории. Там же лежат числа, на
которые ссылается этот файл, и инструменты, которыми они получены:
`detector_conf_sweep.py`, `ocr_engine_compare.py`, `dataset_overlap.py`,
`pipeline_metrics.py`.

Здесь их нет нарочно: этот репозиторий про то, что работает, а не про то, как
выбирали.
